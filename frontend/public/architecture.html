The unique code index supports link lookup. idx_clicks_link_id supports counts by link, and /api/links aggregates clicks before joining so the count stays on an index-only scan rather than reading every click row. There is no denormalised counter column on links: it would make history reads constant-time, but every redirect would then lock the same link row, which costs far more than the scan saves. A separate migrations table records the completed SQLite import. Timestamps use UTC. Existing history was copied into PostgreSQL; SQLite is no longer on the redirect path.

CURRENT BOUNDARIES

Process-level parallelism.

Each of the eight FastAPI workers owns an asynchronous psycopg pool with 2 minimum and 20 maximum connections. Combined capacity is 16–160 pooled PostgreSQL connections, and PostgreSQL runs with max_connections=200 and shared_buffers=512MB to accommodate them. A request commits on success or rolls back on error, then returns its connection for reuse. Checkout waits up to 3 seconds with at most 100 queued callers per worker; exhaustion returns HTTP 503. /api/health reports the responding worker PID and that worker’s pool statistics.

Handlers are async def. The synchronous form dispatched every request to a worker thread, and that handoff plus GIL contention cost more CPU than the queries themselves. The consequence to remember: a genuinely blocking call inside a handler now stalls its whole worker rather than one thread, so database and network work must stay awaited.

Each worker keeps an in-memory map from short code to link id and target URL. Codes and targets are immutable after creation, so entries never need invalidating, and a code created by another worker simply misses once. Unknown codes are not cached, which bounds the map by the number of real links. The click insert is never cached and still commits before the redirect returns.

Uvicorn’s parent and the operating system distribute connections among eight workers behind one container endpoint. Nginx still sees one backend service, so this is multi-process scaling inside the container rather than multiple backend containers. There is no Redis cache, background write queue, or database replica.

Startup order: PostgreSQL becomes healthy → eight workers start and initialise their pools → schema creation and the advisory-locked legacy migration complete safely → Loadgen starts after backend health → Nginx starts after both services are healthy. Docker volumes preserve data across container replacement.

HOW THE LOAD GENERATOR AVOIDS FLATTERING THE APP

An honest number, or none.

The generator runs in its own container and requests http://frontend/{code}, so its traffic traverses Nginx and then FastAPI exactly as a browser’s does, carrying browser User-Agent and Accept headers. Its measurements therefore include Nginx request handling, worker dispatch, FastAPI, pool waiting, and database work. They exclude only the public network and destination page loading, because the 307 is not followed — every result states redirects_followed: false rather than leaving it implied.

Load is offered open-loop: requests fire on a fixed schedule derived from the target rate and do not slow down when the server does. A closed-loop test that waits for each reply before sending the next cannot tell a fast server from one that was never asked for much. Latency is measured from each request’s scheduled arrival rather than from when it was sent, so queue wait is counted instead of vanishing from the percentiles.

Throughput counts only replies delivered inside the measurement window. Replies that drain afterwards are reported separately as late, and requests still unanswered after a ten-second grace period as abandoned; both count against the error rate. Without this rule an overloaded server looks like it kept up, simply reporting its backlog as throughput.

Six processes spread the schedule across CPU cores, and each reports the CPU it consumed while offering load — measured over the offering window only, so an idle drain period cannot average the figure down. When a run exceeds what the generator can offer, the result says so and the UI labels the rate a floor rather than a measurement. Raw keep-alive sockets replaced an HTTP client library that cost roughly ten times the CPU per request and had made the generator, not the application, the limit.

800 rps is the usable ceiling — the highest offered rate the application still keeps up with while tail latency stays reasonable. Saturation throughput is roughly 850–940 rps: past the knee, offering more work does not produce more completed work, only deeper queues and later replies.

The binding resource is CPU, not the database or the disk. At 1500 rps offered the machine is fully committed: backend about 708%, PostgreSQL 249%, Nginx 116%, and the generator 121%, totalling roughly 1194% of the 1200% available. Because the generator consumes about 1.2 cores of that, measuring on the same machine costs roughly a tenth of the ceiling; a client on separate hardware would record a somewhat higher figure.

Two levers remain before hardware. Stopping unrelated containers returns a few percent. Batching click inserts — buffering them in memory and flushing periodically — would remove the per-redirect commit that dominates backend CPU, and would clear 1000 rps; it would also end the guarantee that every redirect commits before it responds, at the cost of losing a fraction of a second of clicks on a crash. That trade has not been made: the current implementation still commits every click.
