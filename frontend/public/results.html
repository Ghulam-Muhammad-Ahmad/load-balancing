How to read this comparison

Stages 01–04 are not comparable with stage 05. Their generator was closed-loop and single-process: it waited for each reply before sending the next, and its HTTP client saturated one CPU core at roughly 115 requests/second. It also measured latency from the moment a request was sent, so time spent queuing never reached the percentiles, and it credited every eventual reply as throughput no matter how late it arrived. Those runs describe the measuring instrument as much as the application, which is why adding API workers appeared to make things worse at stage 04.

The stage-05 generator offers a fixed arrival rate that does not slow down when the server does, measures latency from each scheduled arrival so queue wait is counted, credits only replies delivered inside the measurement window, and reports the CPU it consumed so a generator-bound run is visible rather than mistaken for an application limit. Using raw keep-alive sockets it needs about 0.15 of a core to offer 1000 requests/second, against the 8.7 cores the previous client needed for the same rate.

On the application side, converting handlers from synchronous to async def was the largest single gain, roughly 550 to 890 requests/second: the synchronous form dispatched every request to a worker thread, and that handoff plus GIL contention cost more CPU than the queries. Disabling the Nginx access log on the redirect route removed another bottleneck, as Nginx had been spending about 8.8 cores writing one log line per redirect through Docker’s json-file driver. Raising each pool from 8 to 20 connections removed checkout queuing that had been delaying most requests while PostgreSQL still had spare capacity.

The measured ceiling is now 794 requests/second sustained at 800 offered, with saturation between roughly 850 and 940. The binding resource is CPU: at 1500 offered, the backend uses about 708%, PostgreSQL 249%, Nginx 116% and the generator 121%, close to the 1200% available on this 12-core machine. The next useful change would be batching click inserts, which would end the guarantee that every redirect commits before it responds.
